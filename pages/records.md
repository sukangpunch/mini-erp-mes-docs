# records

해 보고 남긴 기록을 모으는 폴더입니다. 계획서의 산출물 중 "실제로 재고 확인한 것"이 여기에 쌓입니다. 이력서와 면접에서 근거로 제시할 자료입니다.

아직 기록은 없습니다. 첫 기록이 생길 때 아래 폴더를 만듭니다.

| 폴더 | 무엇을 남기나 | 생기는 단계 |
| --- | --- | --- |
| `tuning/` | 쿼리 튜닝. 대상 쿼리, 실행계획, 전후 응답 시간 | 1 |
| `collector/` | 수집기 검증. 중복, 지연, 순서 뒤바뀜을 주입한 테스트의 결과 | 2 |
| `load-test/` | 수집기 부하 시험. 초당 처리량, 어디서 막히는지, 대기열에 쌓이는 양 | 2 |
| `evaluation/` | 에이전트 평가. 평가셋, 지표, 개선 이력, 비용 최적화 전후 | 5 |

## 쓰는 규칙

- **파일 하나에 실험 하나.** 이름은 `YYYY-MM-DD-무엇을.md`로 합니다. 예: `2026-12-10-defect-rate-by-line.md`
- **전과 후를 같이 적습니다.** 바꾸기 전의 숫자가 없으면 개선을 말할 수 없습니다. 그래서 인덱스는 처음부터 다 만들지 않고 재 본 뒤에 추가하기로 했습니다.
- **다시 해 볼 수 있게 적습니다.** 데이터 규모, 실행한 명령이나 SQL, 환경(로컬인지 서버인지, 메모리)을 남깁니다.
- **실제로 나온 숫자만 적습니다.** 예상이나 추정은 추정이라고 표시합니다.

## 검증 기록의 세 칸

수집기 검증과 평가 보고서는 다음을 나눠 적습니다.

| 구분 | 내용 | 예 |
| --- | --- | --- |
| 속성으로 검사한 것 | 무작위 입력 전체에 대해 성립을 확인한 규칙 | 승인 준수, 수집기 멱등성 |
| 표본으로 확인한 것 | 정해진 사례에서만 확인한 동작 | 평가셋 30~50문항, 시나리오 3종 |
| 가정한 것 | 직접 검증하지 않고 믿은 외부 동작 | 브로커의 QoS 1 전달 보장, Oracle의 유니크 제약, LLM 응답 형식 |

## 튜닝 기록의 틀

```markdown
# 제목: 무엇을 빠르게 했는가

- 날짜, 환경, 데이터 규모

## 대상 쿼리
## 바꾸기 전: 실행계획과 응답 시간
## 무엇을 바꿨나, 왜 그것을 골랐나
## 바꾼 뒤: 실행계획과 응답 시간
## 다른 DB에서는: 이 쿼리가 쓴 Oracle 고유 문법과 PostgreSQL, SQL Server에서의 대응
## 치른 것 (적재 속도, 저장 공간 등)
```
