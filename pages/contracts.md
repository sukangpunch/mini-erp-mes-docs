# 계층 사이 계약의 뼈대

구성 요소들이 서로 주고받는 것의 목록입니다. "무엇이 있는가"까지만 정했고, 메시지의 칸 하나하나와 API의 요청, 응답 형식은 각 파트를 개발할 때 정합니다.

- 정한 날: 2026-11-24
- 같은 개념이 계층마다 어떤 이름으로 나타나는지는 같은 폴더의 `ontology.yaml`에 있습니다.
- 계약을 바꿀 때는 양쪽 구현과 이 문서, 온톨로지를 한 커밋에서 같이 고칩니다 (`.claude/skills/contract-change`).

| 연결 | 방식 | 절 |
| --- | --- | --- |
| simulator ↔ core | MQTT (브로커는 RabbitMQ) | 1 |
| agent ↔ core | MCP | 2 |
| web ↔ core | REST API, SSE | 3 |
| web ↔ agent | HTTP 스트리밍 | 4 |

## 공통 규칙

- **가리키는 이름**: 메시지와 API에서는 내부 번호(`_id`)가 아니라 사람이 읽는 코드로 가리킵니다. 설비는 설비 코드(`eq07`), 작업지시는 작업지시 번호, 수주는 수주번호(`order_no`), 자재는 LOT 번호입니다. 고객 발주번호(`customer_po_no`)로 수주를 찾는 것은 지금은 없습니다.
- **시각**: 한국 시간, 1000분의 1초까지. `2026-11-23T14:05:12.418` 형식입니다.
- **순서**: 도착한 순서를 믿지 않습니다. 메시지에 적힌 시각으로 판단합니다.
- **중복**: 설비가 보내는 사건에는 종류마다 설비별로 올라가는 순번이 있습니다. (설비, 순번)이 같으면 같은 메시지입니다.

## 1. simulator ↔ core: MQTT

### 사건과 계측값

설비가 보내는 것은 성격이 다른 두 가지입니다.

| | 사건 | 계측값 |
| --- | --- | --- |
| 무엇 | 일이 일어났다는 보고 | 지금 이 순간의 값 |
| 언제 | 일이 일어났을 때만 | 2초마다 |
| 하나를 놓치면 | 안 됨. 생산 수량이 틀림 | 괜찮음. 다음 값이 곧 옴 |
| 보내는 방법 | QoS 1 (받았다는 확인이 올 때까지 다시 보냄) | QoS 0 (한 번 보내고 끝) |
| 저장 | 전부 | 화면으로 흘려보내고 1분 요약만 저장 |

### 토픽

토픽은 `factory/{설비 코드}/{종류}`입니다. 라인은 넣지 않습니다. 라인은 메시지를 보내지 않고, 설비의 소속 라인은 DB가 알고 있습니다. 토픽에 점(`.`)을 쓰지 않습니다.

| 메시지 | 토픽 | 방향 | QoS | retained | core의 대기열 | 적는 곳 |
| --- | --- | --- | --- | --- | --- | --- |
| 사이클 | `factory/{설비}/cycle` | 설비 → core | 1 | 아님 | `events.cycle` | `cycle_log` |
| 설비 상태 | `factory/{설비}/status` | 설비 → core | 1 | 아님 | `events.status` | `equipment_status_log` |
| 검사 결과 | `factory/{설비}/inspection` | 설비 → core | 1 | 아님 | `events.inspection` | `defect_record` |
| 자재 투입 | `factory/{설비}/charge` | 설비 → core | 1 | 아님 | `events.charge` | `material_charge`, `stock_movement` |
| 계측값 | `factory/{설비}/telemetry` | 설비 → core | 0 | 아님 | `telemetry` | 화면, `equipment_telemetry_1m` |
| 연결 상태 | `factory/{설비}/connection` | 설비 → core | 1 | 맞음 | `events.connection` | 화면의 알람 |
| 작업지시 | `factory/{설비}/order` | core → 설비 | 1 | 맞음 | (설비가 직접 구독) | |

### 메시지에 담기는 것

| 메시지 | 담기는 것 | 중복 판별 |
| --- | --- | --- |
| 사이클 | 작업지시 번호, 찍은 시각, 사이클 타임, 공정값(배럴 온도, 금형 온도, 호퍼 온도, 사출 압력, 사출 속도, 충전 시간, 쿠션). 조립 설비는 공정값이 없음 | 설비 + 사이클 순번 |
| 설비 상태 | 새 상태(가동, 대기, 셋업, 고장, 비가동), 바뀐 시각, 정지 사유 | 설비 + 상태 순번 |
| 검사 결과 | 작업지시 번호, 발견한 시각, 불량 유형별 수량 | 설비 + 검사 순번 |
| 자재 투입 | LOT 번호, 부은 시각, 부은 양 | 설비 + 투입 순번 |
| 계측값 | 보낸 시각, 지금의 온도와 압력, 사이클 진행률, 지금 상태 | 없음. 놓쳐도 됨 |
| 연결 상태 | 연결됨 또는 끊김 | 없음. 마지막 값만 의미가 있음 |
| 작업지시 | 작업지시 번호, 금형, 품목, 계획 수량, 시작 시각. 그 설비의 지금 할 일 | 작업지시 번호 |

### 브로커가 맡는 것

브로커는 RabbitMQ(MQTT 플러그인)입니다. 설비는 MQTT로 발행하고 core는 AMQP 대기열에서 꺼내 받습니다.

| 대기열 | 디스크 저장 | 길이 제한 | 처리 확인 | 계속 실패하면 |
| --- | --- | --- | --- | --- |
| `events.*` (다섯 개) | 함 | 없음 | DB에 넣은 뒤 | 따로 빼 두는 대기열로 보냄 |
| `telemetry` | 안 함 | 있음. 넘치면 오래된 것부터 버림 | 받는 즉시 | 버림 |

- MQTT 토픽 `factory/eq07/cycle`은 RabbitMQ 안에서 `amq.topic` 익스체인지의 라우팅 키 `factory.eq07.cycle`이 됩니다. 대기열은 `factory.*.cycle`처럼 묶습니다.
- **작업지시는 core가 MQTT 클라이언트로 발행합니다.** AMQP로 발행하면 retained가 되지 않습니다.
- **설비는 자기 작업지시 토픽을 정확한 이름으로 구독합니다.** 와일드카드 구독에는 retained 메시지가 전달되지 않습니다.
- **연결 상태**: 설비가 붙을 때 "연결됨"을 retained로 발행하고, 유언(LWT)으로 "끊김"을 맡겨 둡니다. 설비가 갑자기 사라지면 브로커가 "끊김"을 대신 발행합니다.
- QoS 2와 공유 구독은 RabbitMQ가 지원하지 않으며 쓰지 않습니다.

위 동작은 RabbitMQ 4.4.1 컨테이너에서 직접 확인했습니다(2026-11-24).

## 2. agent ↔ core: MCP

### 규칙

- 에이전트는 DB에 직접 접근하지 않고 MCP 도구만 호출합니다.
- 많은 줄을 모아야 하는 것은 core가 DB에서 계산해 작은 결과로 돌려줍니다. 사이클 로그를 통째로 돌려주는 도구와 SQL을 실행하는 도구는 만들지 않습니다.
- 변경은 변경안 등록 → 사람 승인 → 실행의 3단계입니다. 승인과 거절은 도구가 아닙니다. 사람이 화면에서 하고 core의 API로 갑니다.
- 권한 검사는 MCP 서버가 합니다. 사용자의 JWT를 에이전트가 그대로 전달합니다.
- 사건 주입은 도구에 없습니다.

### 도구

| | 도구 | 하는 일 | 종류 | 필요한 역할 |
| --- | --- | --- | --- | --- |
| 1 | `list_equipment` | 라인과 설비의 목록, 지금 상태, 진행 중인 작업지시 | 조회 | 조회 전용 |
| 2 | `get_defect_summary` | 기간과 묶는 기준(라인, 설비, 품목, 불량 유형)별 불량률. 예상 수율과의 차이 포함 | 조회 | 조회 전용 |
| 3 | `get_defect_timeline` | 설비나 작업지시의 시간대별 불량 수 | 조회 | 조회 전용 |
| 4 | `get_material_charges` | 설비에 부은 LOT와 시각, 그 LOT의 공급사와 입고일 | 조회 | 조회 전용 |
| 5 | `get_process_trend` | 설비의 공정값을 시간 구간별 평균으로 (사이클 로그 집계) | 조회 | 조회 전용 |
| 6 | `get_telemetry_trend` | 설비의 계측값 1분 요약. 멈춘 구간 포함 | 조회 | 조회 전용 |
| 7 | `get_equipment_status_history` | 설비의 상태 변화와 정지 사유 | 조회 | 조회 전용 |
| 8 | `search_documents` | 설비 매뉴얼과 작업표준서 검색 | 조회 | 조회 전용 |
| 9 | `get_delivery_risk` | 납기가 가까운 수주 줄 중 위험한 것. 필요 수량, 양품, 재고, 남은 작업지시 | 조회 | 조회 전용 |
| 10 | `get_sales_order` | 수주번호로 수주, 예약, 생산 진척, 출하 | 조회 | 조회 전용 |
| 11 | `get_stock` | 품목의 현재고, 예약, 쓸 수 있는 수, 최근 이동 | 조회 | 조회 전용 |
| 12 | `list_work_orders` | 설비와 날짜별 작업지시와 진척 | 조회 | 조회 전용 |
| 13 | `preview_work_order_change` | 작업지시의 날짜나 설비를 바꿨을 때의 영향 계산. 실행하지 않음 | 미리보기 | 생산 관리자 |
| 14 | `propose_work_order_change` | 변경안 등록. 승인 대기 상태가 됨 | 변경 | 생산 관리자 |
| 15 | `execute_change` | 승인된 변경안 실행. 승인이 없으면 거부 | 변경 | 생산 관리자 |

### 변경의 범위

바꿀 수 있는 것은 작업지시의 날짜와 설비뿐입니다. 수량 변경과 작업지시 취소는 넣지 않았습니다. 만들 물량을 바꾸는 변경이라 사전 검증과 연쇄 처리(조립 작업, 예약)가 크게 늘어납니다. 다른 구현이 끝난 뒤 넣을지 다시 봅니다.

미리보기가 검사하는 것은 납기 초과, 설비의 시간 겹침, 금형의 시간 겹침, 금형과 설비의 조합, 자재 가용량입니다.

## 3. web ↔ core

### API

| 묶음 | 경로 | 하는 일 | 로그인 |
| --- | --- | --- | --- |
| 인증 | `POST /api/auth/login` | 로그인하고 JWT를 받음 | |
| | `GET /api/auth/me` | 내 역할 확인 | 필요 |
| 기준정보 | `GET /api/lines`, `/api/equipment`, `/api/items`, `/api/molds` | 공장 화면과 선택 목록에 쓰는 기준정보 | 없이 가능 |
| 현황 | `GET /api/dashboard/lines` | 라인별 계획 대비 실적, 불량률, 시간가동률 | 없이 가능 |
| | `GET /api/equipment/{코드}` | 설비 상세: 현재 작업지시, 최근 사이클, 불량 추이, 최근 계측값 | 없이 가능 |
| | `GET /api/alarms` | 오늘의 알람 | 없이 가능 |
| 수주와 계획 | `GET /api/sales-orders`, `/api/sales-orders/{수주번호}` | 수주와 줄, 진척 | 필요 |
| | `POST /api/sales-orders` | 수주 수동 등록. 수요 생성 배치도 같은 로직을 씀. 수주번호는 core가 매긴다. 고객 발주번호와 주문한 시각은 보내는 쪽이 줄 수 있다. 같은 고객의 같은 발주번호가 같은 내용(고객, 줄마다의 품목과 수량과 납기. 줄의 순서는 보지 않는다)으로 다시 오면 저장하지 않고 이미 있는 수주를 돌려주고, 내용이 다르면 거절한다. 동시에 온 두 요청도 같은 결과가 된다. 줄 하나라도 틀리면 수주 전체를 받지 않는다 | 생산 관리자 |
| | `GET /api/work-orders` | 설비와 날짜별 작업지시 | 필요 |
| 재고 | `GET /api/stock`, `/api/stock/{품목}/movements` | 현재고와 이동 내역 | 필요 |
| 변경안 | `GET /api/change-requests`, `/api/change-requests/{번호}` | 에이전트가 올린 변경안과 사전 검증 결과 | 생산 관리자 |
| | `POST /api/change-requests/{번호}/approve`, `/reject` | 사람의 승인과 거절 | 생산 관리자 |
| 시연 | `POST /api/demo/incidents` | 사건 주입 (설비 고장 등) | 데모 계정 |
| 실시간 | `GET /api/stream` | SSE 연결 | 없이 가능 |
| 에이전트 전용 | `/mcp` | MCP 도구 호출. 화면은 쓰지 않음 | JWT 전달 |

- 화면에서 사람이 바꾸는 것은 수주 수동 등록, 변경안의 승인과 거절, 사건 주입뿐입니다. 작업지시와 재고는 배치와 수집기가 만들고 화면은 보기만 합니다.
- 작업지시를 화면에서 직접 고치는 API는 없습니다. 변경은 에이전트의 변경안으로만 해서 승인 경로를 하나로 유지합니다.

### SSE 이벤트

화면은 `/api/stream` 하나에 연결하고 이벤트 이름으로 종류를 구분합니다.

| 이벤트 | 언제 | 화면에서 바뀌는 것 |
| --- | --- | --- |
| `equipment.telemetry` | 1~2초마다. 전 설비의 최신 값을 묶어서 | 공장 화면의 금형 움직임(사이클 진행률), 설비 상세의 온도와 압력 |
| `equipment.status` | 설비 상태가 바뀔 때 | 공장 화면의 설비 상태 등 |
| `equipment.connection` | 설비가 붙거나 끊길 때 | 통신 끊김 표시 |
| `work-order.progress` | 1분 재집계가 끝날 때 | 현황판의 계획 대비 실적, 진척률 |
| `work-order.updated` | 작업지시가 생기거나 바뀔 때 | 작업지시 목록 |
| `defect.recorded` | 검사 결과가 들어올 때 | 불량 추이 |
| `alarm.raised` | 고장, 통신 끊김, 불량 급증 | 알람 목록 |
| `change-request.updated` | 변경안이 등록, 승인, 실행될 때 | 승인 화면 |

- 계측값은 들어오는 대로 흘리지 않습니다. core가 설비별 최신 값을 모아 1~2초마다 한 번에 보냅니다.
- 재고가 바뀔 때의 이벤트는 없습니다. 재고 화면은 조회할 때 가져옵니다.

## 4. web ↔ agent

| 경로 | 하는 일 | 로그인 |
| --- | --- | --- |
| `POST /agent/chat` | 질문을 보내고 답을 스트리밍으로 받음 | 데모 계정 이상 |

Nginx가 `/agent`를 agent 서비스로 직접 보냅니다. 에이전트는 받은 JWT를 검증하고 MCP 호출에 그대로 싣습니다. 호출 횟수 제한과 LLM 예산 상한은 agent 서비스가 겁니다.

## 아직 정하지 않은 것

- 메시지와 API의 정확한 형식 (칸 이름, 타입, 필수 여부). 형식은 JSON Schema나 AsyncAPI, OpenAPI로 적을 예정입니다.
- 계측값을 보내는 정확한 간격과 담을 값의 범위
- 알람의 기준 (불량 급증을 무엇으로 판단하는가)
- 변경안과 승인을 적을 테이블 (3단계에서 ERD에 추가)
